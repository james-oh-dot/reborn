# 0. BILINGUAL GOVERNANCE
# 0. 한·영 병행 운영 원칙

이번 프로젝트의 모든 후속 산출물은 **한국어 원문을 먼저 만들고 영어를 나중에 번역하는 방식이 아니라**, 처음부터 한국어와 영어를 각각 독립적으로 읽어도 자연스럽게 설계한다.

All subsequent deliverables must be developed **natively in both Korean and English from the beginning**, rather than writing Korean first and translating it into English at the end.

## 0.1 Core Rule / 핵심 규칙

- Korean and English must communicate the **same strategic meaning**, but do not need to follow identical sentence structures.
- 한국어와 영어는 **동일한 전략적 의미**를 전달해야 하지만 문장 구조까지 직역할 필요는 없다.
- English must read like corporate English written for international partners, not translated Korean.
- 영어는 번역투가 아니라 해외 파트너가 자연스럽게 읽는 기업 영어여야 한다.
- Korean must remain concise and contemporary, avoiding old-style IR or government-report language.
- 한국어 역시 과거 IR·정부과제식 문체를 피하고 현대적인 기업 언어를 사용한다.
- Every menu, section title, CTA, capability label, project status, and metadata field must have a paired KR/EN definition.
- 모든 메뉴, 섹션 제목, CTA, 역량명, 프로젝트 상태, 메타데이터에는 KR/EN 대응어를 둔다.

# 1. INFORMATION ARCHITECTURE OBJECTIVE
# 1. 정보구조 설계 목표

The website must answer four questions in the shortest possible time.

홈페이지는 방문자가 가능한 한 짧은 시간 안에 다음 네 가지 질문에 답을 얻도록 설계한다.

1. **Who is Rebornsoft? / 리본소프트는 어떤 회사인가?**
2. **What can Rebornsoft do? / 무엇을 할 수 있는가?**
3. **What proves it? / 무엇으로 그것을 증명하는가?**
4. **Why should we talk to them? / 왜 이 회사와 대화를 시작해야 하는가?**

The website is not designed to display every historical fact.  
It is designed to create **understanding → credibility → interest → contact**.

홈페이지는 모든 연혁을 다 보여주기 위한 것이 아니다.  
**이해 → 신뢰 → 관심 → 문의**의 흐름을 만들기 위해 존재한다.

# 5. RECOMMENDED WEBSITE ARCHITECTURE
# 5. 권장 전체 사이트 구조

현재 자료량과 신뢰 구조를 기준으로 **4개의 핵심 페이지 + Home** 구조를 권장한다.

Based on the available content and proof structure, the recommended architecture is **Home + four primary pages**.

---

## 01. HOME / 홈

### Purpose / 목적
회사 전체를 가장 짧고 강하게 이해시키는 Executive Overview.

An executive overview that communicates the company at a glance.

### Must answer
- Who we are
- What we do
- Why we are credible
- Where we are heading

---

## 02. COMPANY / 회사소개

### Purpose / 목적
회사 정체성, 기술적 출발점, 성장 과정, 객관적 신뢰 정보를 설명한다.

Explain identity, technical roots, evolution, and corporate credibility.

### Includes / 포함
- Company Overview / 회사 개요
- Evolution / 성장 과정
- History / 연혁
- Certifications & IP / 인증·특허
- Corporate Facts / 기업 기본정보

---

## 03. CAPABILITIES / 역량

### Purpose / 목적
과거 제품명이 아니라 현재 리본소프트가 프로젝트에서 사용할 수 있는 역량을 설명한다.

Explain what Rebornsoft can apply to projects today, rather than simply listing historical products.

---

## 04. PROJECTS / 프로젝트

### Purpose / 목적
검증 가능한 실제 적용사례와 선택 프로젝트를 보여준다.

Show selected, verifiable applications and projects.

### Principle / 원칙
Project status must remain explicit.

`Developed / Released / Contracted / Installed / Planned`

프로젝트의 실제 Status를 숨기거나 동일한 수준으로 보이게 만들지 않는다.

---

## 05. CONTACT / 문의

### Purpose / 목적
파트너·고객·프로젝트 관계자가 리본소프트와 대화를 시작할 수 있게 한다.

Enable partners and project owners to start a conversation with Rebornsoft.

# 7. WHY HISTORY IS NOT A TOP-LEVEL MENU
# 7. 연혁을 독립 메뉴로 두지 않는 이유

리본소프트는 긴 연혁을 가지고 있지만 `HISTORY`를 Top Navigation으로 독립시키면 사이트가 과거 중심으로 읽힐 수 있다.

Rebornsoft has a meaningful history, but making `HISTORY` a primary navigation item risks making the company feel legacy-focused rather than forward-looking.

따라서:

> **History belongs inside Company.**

연혁은 중요하지만 회사 정체성보다 앞에 나오지 않는다.

History is important evidence, but it should not precede positioning and capability.

---

# 8. WHY "WORK" IS NOT RECOMMENDED AS THE MAIN LABEL
# 8. 메인 메뉴에서 “WORK”를 우선하지 않는 이유

Spectrascape는 `WORK`라는 표현을 사용하지만 리본소프트는 동일한 표현을 그대로 가져오지 않는다.

Spectrascape uses `WORK`, but Rebornsoft should not automatically adopt the same label.

현재 리본소프트 자료에는:

- Installed
- Released
- Contracted
- Co-developed
- Planned
- Proposed

등 서로 다른 상태가 존재한다.

따라서 `PROJECTS`가 더 정확하고 안전하다.

`PROJECTS` allows the website to represent different project states more accurately and transparently.

향후 공개 가능한 완료 프로젝트가 충분히 축적되면 `WORK`로 전환할 수 있다.

# 12. PROJECTS PAGE ARCHITECTURE

Projects는 연도보다 **증거 가치와 현재 Positioning과의 관련성**을 우선한다.

Projects should be prioritized by proof value and relevance to the current positioning, not simply by chronology.

# 13. CONTACT 페이지 구조

# 14. LANGUAGE UX ARCHITECTURE
# 14. 언어 UX 구조

## Recommended
페이지 내에서 한국어와 영어를 동시에 병기하지 않는다.

Do **not** display Korean and English simultaneously throughout the same page.

이유:
- Visual density 증가
- Spectrascape 수준의 강한 이미지 중심 구성 저해
- 모바일 가독성 저하
- 카피 위계 붕괴

### Recommended UX
**KR / EN language switch**

한 시점에는 한 언어만 보여준다.

Show one language at a time.

# 15. LANGUAGE PARITY RULE
# 15. 한·영 콘텐츠 동등성 규칙

모든 공개 페이지는 KR/EN 동일한 정보구조를 유지한다.

Every public page should maintain the same information architecture in Korean and English.

단, 문장 길이와 리듬은 언어별로 최적화한다.

### Example principle

한국어:
> 사람과 시스템이 상호작용하는 기술을 개발합니다.

영어:
> We build technologies that enable people and systems to interact.

직역:
> We develop technology in which people and systems interact.

와 같은 번역투는 피한다.

# 16. ENGLISH COPY STANDARD
# 16. 영문 카피 기준

영문은 다음 성격을 가져야 한다.

- Short
- Native-sounding
- Professional
- Concrete
- Non-hyped
- Easy to scan

피해야 할 문장 구조:

- "Rebornsoft is a company that..."
- "Through various technologies..."
- "Based on differentiated technology..."
- "We will lead the future..."
- "We are striving to..."

한국 기업소개서의 직역형 영어를 사용하지 않는다.

# 17. KOREAN COPY STANDARD
# 17. 국문 카피 기준

한국어 역시 다음을 피한다.

- 당사는
- 최첨단
- 차별화된 기술력
- 4차 산업혁명 시대
- 미래를 선도합니다
- 최고의 서비스를 제공합니다
- 고객가치를 창출합니다

대신 짧고 실제 행동이 보이는 문장을 사용한다.

# 18. INFORMATION DENSITY RULE
# 18. 정보 밀도 규칙

Spectrascape Reference의 장점 중 하나는 **한 화면에 모든 것을 설명하지 않는 것**이다.

리본소프트도 동일한 원칙을 적용한다.

Low to Medium density  
큰 이미지 / 짧은 문장 / 명확한 이동

## Company
Medium density  
연혁·인증·기업 정보

## Capabilities
Medium density  
기술과 설명의 균형

## Projects
Medium to High evidence density  
실제 이미지·역할·상태·기술

# 19. EVIDENCE PLACEMENT
# 19. 증거 배치 원칙

Evidence는 별도의 “자랑 섹션”에 몰아넣지 않는다.

Do not isolate all evidence in one self-congratulatory proof section.

가능하면 관련 정보 옆에서 바로 증명한다.

Examples:

- AI capability → KISA / patent evidence
- Digital environment → 7 Cubic
- Physical experience → VR cafe / simulator
- Project integration → Cityfield contract

이 구조가 `Claim → Proof`의 거리를 줄인다.

# 20. PROJECT VISUAL HIERARCHY
# 20. 프로젝트 이미지 우선순위

1. **Actual Project Photography / 실제 프로젝트 사진**
2. **Actual UI / 실제 서비스 화면**
3. **Actual Installation / 실제 설치 이미지**
4. **Documentary Evidence / 계약·인증·특허**
5. **Concept Visualization / 컨셉 이미지**
6. **Representational AI Image / 표현용 생성 이미지**

하위 항목이 상위 Evidence를 대체해서는 안 된다.

Concept images must never visually overwrite or masquerade as completed project evidence.

# 21. MOBILE INFORMATION PRIORITY
# 21. 모바일 정보 우선순위

모바일에서는 데스크톱 레이아웃을 단순 축소하지 않는다.

Mobile must preserve the information hierarchy, not merely scale down desktop layouts.

우선순위:

1. Positioning
2. Main visual
3. Capability
4. Project proof
5. Contact CTA
6. Detailed history

연혁과 상세 인증 정보는 Progressive Disclosure 방식으로 압축 가능하다.
